## 1. Method statement

This is a code-and-local-run diagnosis, not a production-analytics report. No production PostHog query was made, no production account was created, and no production behavior was changed.

Evidence labels used throughout:

- **Code** means the count or behavior was read from the cited source lines.
- **Observed local run** means it was observed on 2026-07-14 in a local `pnpm dev` session with an uncommitted Playwright command.
- **Estimated** means it is not an observed user-time measurement; its method is stated beside the number.

Reproduction performed:

1. Ran the required local prerequisites: `pnpm install --frozen-lockfile`, `pnpm db:generate`, then the clean-baseline gates `pnpm type-check && pnpm lint && pnpm test`. The baseline passed; lint reported existing warnings only.
2. Read the signup page and both tenant endpoints, the onboarding layout/index/stub routes, the old onboarding service/API, activation/drop-off services, dashboard recommendation service/API/UI, and telemetry tracker. Every behavioral conclusion below has a source citation.
3. Started the local app and used an uncommitted Playwright command. `/signup` returned HTTP 200; the rendered DOM had five required inputs (`owner_name`, `email`, `password`, `team_name`, `team_slug`). Filling only the team name generated the slug and produced two observed availability GETs in that session (one for the initial default slug and one for the edited slug); both returned 503 locally. **Observed local run:** that 503 is recorded only as local-environment behavior, not as a claim about production availability.
4. Direct local visits to `/onboarding`, all six legacy step URLs, and `/dashboard` resolved to `/login` without an authenticated session. **Observed local run:** authentication therefore prevented visual confirmation of the authenticated redirects; the authenticated destination claims below are source-traced from the page-level `redirect()` calls. No signup submit, tenant registration, or database-writing request was executed.

Round-trip convention: the journey table counts browser-visible application/auth HTTP requests that the screen itself initiates. Server-side service/database reads during an SSR render are described but are not misrepresented as browser network calls. Counts with variable user input are ranges or formulas, not a fabricated fixed number.

The canonical funnel vocabulary and risk windows used below are `SIGNUP → AI_INTERVIEW → BUSINESS_ANALYSIS → FIRST_MISSION → FIRST_ASSET → FIRST_OUTCOME → ACTIVATED`. The existing grace periods are 6h, 24h, 24h, 48h, 72h, 7d, and none respectively; the separate first-win risk threshold is 15 minutes. **Code:** `src/modules/activation/contracts/ActivationProjection.ts:29-36`; `src/modules/activation/services/dropoff-detector.ts:10-18,59-98,125-139`.

## 3. Two finish lines, measured separately

### Finish line A — first rendered card of any kind

**Measured path:** Signup → onboarding overview → Skip → dashboard unified mission card: **3 user-visible screens** and **2 transitions after the signup screen**. It has **5 required signup inputs**, **one explicit Skip decision**, and **5 fixed browser-visible operations** before optional slug/telemetry traffic: Supabase signup, tenant registration, Skip POST, dashboard projection GET, and recommendation GET. The slug check is variable (one per qualifying edit) and telemetry identity GET is non-blocking, so neither is included in that fixed count. **Code:** `src/app/signup/page.tsx:42-79,93-132`; `src/modules/member/components/OnboardingShell.tsx:34-45`; `src/modules/dashboard/hooks/useDashboardMission.ts:43-53`; `src/modules/dashboard/hooks/useDashboardRecommendation.ts:19-32`.

**Time:** **Estimated 3–5 min; method:** the §2 signup estimate plus one choice and dashboard rendering. This is an estimate, not funnel analytics. Its risk anchor is the existing 6h `SIGNUP` grace period, and it is well before the 15-minute first-win risk threshold; neither is being introduced as a new target. **Code:** `src/modules/activation/services/dropoff-detector.ts:10-18,125-139`.

**What renders:** with Command Center enabled, the API returns source `rule`, confidence `0.9`, title “Complete the AI Interview,” and route `/brand-builder/step/interview`; C1’s unified `AICommandCard` presents the mission while merging that recommendation explanation rather than showing a separate rule-title card. **Code:** `src/modules/dashboard/services/recommendation-service.ts:199-216,249-274`; `src/modules/dashboard/components/DashboardHome.tsx:154-218`. If the runtime flag is off, the service returns `null`; this is not a recommendation finish. **Code:** `src/modules/dashboard/services/recommendation-service.ts:54-74`; `src/__tests__/services/dashboard-recommendation-service.test.ts:31-64`.

**Stage-A seed-user conclusion:** a seed user is realistically reaching **Finish line A’s cold-start rule**, most directly through the visible Skip path. They are not yet reaching an engine-driven recommendation merely by seeing this card.

### Finish line B — first engine-driven recommendation

**Measured eligibility:** the dashboard result is source `engine` only after `resolveColdStartRule()` returns `null`. That requires all of the following: Command Center enabled; no `MISSION_AI_INTERVIEW`; no missing `AI Interview Completed`; no `NO_CONTENT` bottleneck and no `CONTENT_SYSTEM` current Business State; and not both analytics readiness and progress below 20. **Code:** `src/modules/dashboard/services/recommendation-service.ts:58-91,199-247,285-302`.

**Minimum counted route sequence, not a promise of completion:** Signup → onboarding overview → `/brand-builder/step/interview` → `/brand-builder/step/profile` → dashboard: **5 user-visible screens**. The interview client creates/loads an interview, submits one request per dialogue message, and posts a finish request before routing to profile; message count is intentionally open-ended, so there is no honest fixed request or input count. **Code:** `src/modules/brand-builder/components/wizard/InterviewStepClient.tsx:331-402,404-445`; `src/app/(auth)/brand-builder/step/interview/page.tsx:1-18`.

**Time:** **Estimated lower bound 10–12 min; method:** 2–4 min estimated signup plus the currently authoritative AI interview mission estimate of 8 min, then dashboard render. **Code:** `src/modules/mission-engine/services/MissionEngineAuthorityService.ts:50-60`. This lower bound excludes the non-deterministic extra actions needed to satisfy the remaining Business State/analytics predicates, so **a total time to Finish line B cannot be truthfully bounded from the current code**. That is a measurement result, not missing analysis.

**Why the lower bound is insufficient for most new users:** Business State has ordered capability requirements; the engine-rule path still intercepts `CONTENT_SYSTEM`, whose requirements include content pillars, calendar, minimum assets, and content-engine activation. **Code:** `src/modules/business-state/services/business-state-capability-engine.ts:54-97,155-202`; `src/modules/dashboard/services/recommendation-service.ts:219-246`. The first-win detector also marks no generated first content after 15 minutes as missed for risk evaluation. **Code:** `src/modules/activation/services/dropoff-detector.ts:125-139`.

**Stage-A seed-user conclusion:** the realistic result is **not Finish line B**. A seed user must first establish interview and further runtime signals; seeing the deterministic rule is the intended current entry point.

## 4. Friction findings, ranked by estimated drop-off likelihood

Ranking is **estimated, method: number of required decisions/fields, visible detours, and blocking behavior from the traced code**. It is not a production conversion ranking.

1. **High — legacy five-step progress chrome contradicts the actual screen and routes.** The shell always renders five dots and “Step _ of 5”; at `/onboarding` the unmatched path is coerced to step 1, yet the only real index content is the activation overview. **Code:** `src/modules/member/components/OnboardingShell.tsx:10-31,47-96`; `src/app/(auth)/onboarding/page.tsx:11-40`. An authenticated user who follows a named legacy step does not get the advertised step; each stub redirects to a different module as detailed in §2. This loses beginner confidence because the screen says they are in a five-step wizard while the next page can be a separate product module. **Funnel step:** `AI_INTERVIEW` (entry) and subsequent hand-offs. **Candidate result:** confirmed.

2. **High — Skip silently marks onboarding complete and sends the user to dashboard before the AI interview.** One click POSTs the legacy skip endpoint, sets `completed: true`, then `window.location.replace('/dashboard')`; there is no confirmation or explanation of the effect. **Code:** `src/modules/member/components/OnboardingShell.tsx:34-45`; `src/app/api/v1/member/onboarding/route.ts:26-30`; `src/modules/member/services/onboarding-service.ts:267-275`. This creates the fastest path to a dashboard that tells a cold-start user to complete the AI interview, rather than carrying them directly into that mission. **Code:** `src/modules/dashboard/services/recommendation-service.ts:199-216`. **Funnel step:** `AI_INTERVIEW`. **Candidate result:** confirmed.

3. **Medium-high — the signup form asks for five required values and presents a paid-plan decision before value is shown.** All five inputs are required, while three plan cards (including RM 99/RM 299) are visible above account creation. **Code:** `src/app/signup/page.tsx:14-18,149-258`. The plan is defaulted to `starter`, so the stricter claim “a plan choice blocks signup” is dismissed; the friction is decision exposure and perceived commitment, not validation. **Funnel step:** `SIGNUP`. **Candidate result:** confirmed, with the blocking claim dismissed.

4. **Medium — slug availability adds an asynchronous gate during signup.** The page auto-generates a slug, debounces 350ms, calls the availability endpoint, and disables submit while checking or when taken. **Code:** `src/app/signup/page.tsx:36-79,191-221,252-258`. **Observed local run:** two availability GETs occurred during one initial-and-edit interaction; both were 503 locally, which is not production evidence. The endpoint also performs rate limiting and a tenant lookup. **Code:** `src/app/api/v1/tenant/check-slug/route.ts:22-52`. **Funnel step:** `SIGNUP`. **Candidate result:** confirmed.

5. **Medium — legacy onboarding state is still reachable and can diverge from the activation journey.** The authenticated layout reads `onboardingService.getState()` for every authenticated route; Skip writes it, and the active brand-builder completion client still PATCHes the old `brand` step. **Code:** `src/app/(auth)/layout.tsx:15-28`; `src/modules/member/components/OnboardingShell.tsx:34-45`; `src/modules/brand-builder/components/wizard/CompleteStepClient.tsx:10-23`. The service/API remains live and persists the old step model, while the old pages are redirect stubs. **Code:** `src/modules/member/services/onboarding-service.ts:13-35,238-315`; `src/app/api/v1/member/onboarding/route.ts:8-30`. This is reachable state, not dead code; it can make completion/navigation affordances disagree with the activation mission. **Funnel step:** cross-cutting; most visible at `AI_INTERVIEW`. **Candidate result:** confirmed.

6. **Medium — “first AI recommendation” is easy to overstate.** A fresh user receives a deterministic rule before the engine is consulted, while the engine requires additional Business State and analytics conditions. **Code:** `src/modules/dashboard/services/recommendation-service.ts:58-91,199-302`. A user or stakeholder can interpret the visible unified mission card as AI-personalized progress even though its first recommendation is a fixed cold-start safety rule. **Funnel step:** `AI_INTERVIEW` → `BUSINESS_ANALYSIS`. **Candidate result:** confirmed.

### Measurement limitation for G2 hand-off

The tracker includes signup, content/funnel, recommendation, discussion, upgrade, and weekly-active events, but no per-onboarding-step event. **Code:** `src/lib/telemetry/tracker.ts:43-78`. Consequently, this exact journey cannot currently be measured in PostHog at per-step granularity. Confirming whether the existing events flow in production is explicitly G2 work and was not attempted here.
