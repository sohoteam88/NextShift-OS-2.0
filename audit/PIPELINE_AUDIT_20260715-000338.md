## CP3 — F1 P0 signup break (dangling accounts)

**This is the highest-stakes item in the round** — a production-level break where verified users could end up with a Supabase auth identity but no tenant. I traced the whole chain rather than reading the PR description.

**Root cause, confirmed:** `/api/v1/tenant/register` rejects unverified sessions (`route.ts:14`, `EMAIL_VERIFICATION_REQUIRED`, 401). When email confirmation is on, `signUp` returns **no session**, so the client could never legally reach the register call — and nothing else ever provisioned the tenant. The account was stranded by design.

**The fix is a complete chain, and each link is real:**

1. **Signup stashes the intent** (`signup/page.tsx:97-110`): `name`, `slug`, `plan`, `owner_name`, `locale` go into Supabase `user_metadata`, with `emailRedirectTo` pointed at `/auth/callback`. The intent survives the email round-trip — this is what makes post-verification provisioning possible at all.
2. **No session → explicit UI state, not a silent stall** (`:118-121`, `setVerificationRequired(true)`).
3. **`/auth/callback` is the compensation path** (`auth/callback/route.ts`): exchanges the code for a session, re-checks `isVerifiedSupabaseUser`, reads the intent from `user_metadata`, calls `tenantProvisioningService.provision`, and redirects to `/onboarding`. Provisioning failure redirects to `/setup-workspace?error=provisioning_failed` rather than dead-ending.
4. **`/setup-workspace` recovers pre-existing dangling accounts** — the ones already stranded in production, who have no callback to replay.
5. **Both entry points fund through one owner.** `tenantProvisioningService` is the *only* provisioning implementation, called from exactly two places (the callback and the register route). There is no second, divergent path.

**The provisioning service is correctly hardened** (`tenant-provisioning-service.ts`):
- **Idempotent** — `findExistingProvisioning(user.id)` runs first inside the retry loop and returns `created: false` if a tenant already exists (`:141-142`). Replaying a callback link cannot double-provision.
- **Verified-email gate is enforced in the service**, not just at the route (`:136-138`) — defense in depth.
- **Slug collisions resolved** against reserved words and existing tenants before insert (`:92-103`).
- **Concurrent-signup race handled**: a `P2002` unique violation is caught and re-resolved via `findExistingProvisioning` (`:164-167`), so two racing requests converge on one tenant instead of erroring.
- **`trackUserSignedUp` fires only on the `created` path** (`:157`) — so the event is emitted once per real signup. **This is what makes G2's fifth event observable**; its absence was the reason G2 could not verify `user_signed_up`.

**Copy is genuinely trilingual, as claimed** — `emailVerificationRequired` exists in `en`/`ms`/`zh` with real translations (not placeholders), and the new `/setup-workspace` page routes through `useTranslations('auth')` with **zero** CJK literals. The prior round's i18n defect class was not repeated here. ✓

**E2E regression coverage exists and is real:** `auth.spec.ts:59` — *"a dangling authenticated account finishes workspace setup and reaches the dashboard"* — backed by a dedicated dangling fixture in `helpers/auth.ts:8-9` supplied by `scripts/ensure-e2e-user.ts`. This ran green in CI (36 E2E tests). ✓

**Result: CP3 PASS** — with production verification still outstanding (C-3).

## Verdict

**PASS WITH CONDITION.**

The prior round's FAIL is genuinely resolved, and resolved in the way that matters: not by an auditor re-running the suite locally, but by the pipeline itself. `lint:boundaries:check` is in sync, PR #73 went green across all four checks including an 8-minute E2E run, and I confirmed by subtree hash that the code CI exercised is **byte-identical** to the code at HEAD. Last round T1 sat on this branch having never been executed by a single CI job; that is no longer true of anything here.

The work itself holds up under real inspection. T2's prompt injection is bounded, ordered, skips cleanly on an empty Twin, carries a "do not infer" guardrail, and is backed by tests that assert each of those properties separately rather than in a lump. G3 didn't just rewire the four call sites — it **deleted the function**, so the bypass cannot come back, and I verified the router does not self-enforce quota, meaning the new voice gate closes a real hole rather than double-charging. F1, the P0, is a coherent chain from `user_metadata` through `/auth/callback` to an idempotent, race-safe provisioning service that also restores the `user_signed_up` event G2 couldn't see. Local type-check, lint (0 errors), 468 tests, build, and i18n (1393 × 3, zero missing) are all green.

It is not a clean PASS for two reasons, and neither is a bug in what shipped. First, **release criterion #5 demands E2E coverage for the Twin summary and there is none** — the requirement was set aside by manual adjudication and recorded in a code comment. I think the judgment is right; CI has no LLM keys and cannot see inside a prompt. But an auditor cannot mark a criterion met by agreeing with the reason it was skipped, and the blueprint should say what the project actually decided. Second, **the exact prompt-noise defect the last audit forecast has now materialized**: for any `BrandProfile` user the system prompt presents the same positioning statement three times under three labels, plus the business name twice, in a block that tells the model these are verified facts. The previous audit said to fix it *before* T2 because it would be awkward afterward. It is now afterward.

Both are cheap to close, and neither justifies holding the branch. Ship-blocking issues: **none**.
