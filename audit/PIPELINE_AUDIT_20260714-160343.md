## CP1 — T1 Business Twin real data wiring (release criterion #4)

**Requirement:** replace the `discussion-service.ts:214` hardcoded stub; `identity` reads from `interview-authority`, `brand` (`BrandDNAContext`) reads from `brand-dna`; users who never did Interview/Brand DNA get an explicit empty-value degradation — **not an error, and not hardcoded fake data**.

**The stub is genuinely gone.** The prior `identity: { businessName: 'NextShift Command Center', values: ['clarity', 'momentum'] }` literal is deleted. `buildDiscussionDecisionContext` now spreads conditionally (`:223-224`):

```ts
...(businessTwin?.identity ? { identity: businessTwin.identity } : {}),
...(businessTwin?.brand   ? { brand:    businessTwin.brand    } : {}),
```

so a user with no data gets **no `identity` key at all**, rather than a fake one. ✓

**Real sources, both wired** (`src/modules/business-twin/services/interview-brand-business-twin-repository.ts`):
- `identity` ← `interviewAuthorityService.getInterviewAuthority(userId)` (`InterviewProfileSnapshot` → `industry`, `missionStatement`; `BusinessContextSnapshot` → `businessStage`) plus `brandContext` for `businessName`/`positioning`. ✓
- `brand` ← `getBrandContext(userId)` from the `brand-dna` module (`brandName`, `elevatorPitch`/`coreMessage` → `brandStory`, `tone` → `voice`, `positioning`). ✓
- The class implements the real `BusinessTwinRepository` interface from `@nextshift/business-brain`, so the contract is honored rather than bypassed. ✓
- Both loads run in `Promise.all` (`:29`), so T1 adds one round-trip of latency, not two.

**No fake data — verified down to the adapters, which is where this could have gone wrong.** The repository treats `confidence === 'fallback'` as "not real" and discards those snapshots (`:62-67`). I traced what actually produces `'fallback'`: a user with no `brandProfile`, no `brandInterview`, and no legacy profile falls through `assembleInterviewAuthority` to `adaptOnboardingContextToInterviewAuthority`, which stamps `confidence: 'fallback'` on all three snapshots (`OnboardingContextAdapter.ts:30,46,61`). Those are exactly the synthesized defaults, and they are exactly what T1 filters out. Real data is stamped `'confirmed'` (`BrandProfileAdapter`) or `'derived'` (`BrandInterviewAdapter`) and is kept. Every field additionally passes through `stringValue()` (`:99-101`), which drops empty/whitespace/non-string values. **This directly discharges the blueprint's risk-table row 2** ("把用户没填的字段当成『已知』注入 prompt"). ✓

**Full empty degradation:** if neither `identity` nor `brand` has a single populated field, `getSnapshot` returns `null` (`:36`) — no error, no placeholder. ✓

**Result: CP1 PASS.**

## CP3 — Does the Twin data actually reach the model? (scope boundary between T1 and T2)

**No — and today that is correct, but it should be understood plainly.** The loaded snapshot flows into `DecisionContext.businessContext` (`:218-245`) and **stops there**. `DecisionContext` is consumed only by `conversationEngine.continueConversation(decisionContext)`, and `RecommendationDiscussionEngine` reads nothing from it except `context.decisionContextId` (`:187-206`). `buildSystemPrompt(recommendation, conversationSnapshot, memory)` (`:134`, `:286-309`) has **no twin parameter** and ends at the OS 3.6 `buildMemorySummary` injection.

So **the AI never sees the Twin data.** The project's own test confirms the boundary — it asserts the twin lands in the *decision context*, never in the prompt.

This is faithful to the blueprint: prompt injection is **T2**, explicitly a separate task, and release criterion #4 (T1) only demands that the snapshot stop being a stub. **Criterion #4 is met.** But two consequences follow that are worth stating rather than discovering later:

- **T1 has zero user-visible or model-visible effect until T2 lands.** Nothing about discussion quality changes today.
- **It is not free.** Every discussion turn now issues ~4–5 extra Prisma queries for data that currently influences nothing (see F-4).

**Result: CP3 PASS** (correctly scoped; advisories F-3/F-4).

## Verdict

**FAIL.**

Not because the feature is wrong — **T1 is good work.** The stub is genuinely gone, `identity` and `brand` are wired to real Interview and Brand DNA data through the real `BusinessTwinRepository` interface, and the degradation the blueprint insisted on is real and tested: users who never completed Interview or Brand DNA get **no `identity` key at all** rather than a fabricated one, verified all the way down to the adapters that stamp `confidence: 'fallback'` on synthesized defaults. The read-failure safety net logs through `runtimeFallbackLogger` and lets the discussion continue. Both prior-round conditions are cleared — the user-visible i18n defect is fixed (0 CJK literals remain in the two cards; 1384 keys × 3 locales) and C2 is marked complete.

The failure is that **the branch does not pass its own gate.** `lint:boundaries:check` is a required CI step and it fails at HEAD on a clean tree, because T1 added a new module and never regenerated `eslint-boundaries.config.mjs`. CI run `29317776466` is red. **PR #69 was merged over that red check**, and because the build job failed, the `Tests` and both `E2E` jobs were **skipped entirely** — so the T1 code now sitting on the integration branch has **never been validated by CI at all**, and unlike the last round there is no byte-identical green run to fall back on. I ran everything locally and it is green, but "it passes on the auditor's machine" is not the standard this gate exists to enforce.

The remediation is one command and a commit, and I verified it is safe (boundaries green; lint 0 errors, +4 advisory warnings). But an integration branch with a failing required check, carrying a feature no CI job has ever exercised, is not a PASS — and the fact that a red gate could be merged past is the finding that deserves the most attention here.

Separately, for planning rather than for this verdict: five of the nine v3.7.0 release criteria remain unmet, and Phase-0 items G2 and G3 are still untouched while every later phase has shipped.
