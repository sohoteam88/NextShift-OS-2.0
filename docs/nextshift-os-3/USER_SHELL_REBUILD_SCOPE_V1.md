# 第零章 · 六条护栏

**范围清单的每一条都受这六条约束。冲突时以本章为准。**

1. **只重建 UI 壳层**（页面 / 组件 / 路由）。后端服务与 API（G0-G5、事业包、Brand DNA、漏斗服务）一律复用，**不许顺手重写**。
2. **现有用户面页面不删**。整体挪到 admin 区（修正案既定：降为 super admin 工具），用户路由指向新壳。
3. **新壳三页封顶**：首页 / 内容页（发）/ 跟进页（跟）。「投」（广告陪驾）属 W4 T5，**留插槽不实现**。
4. **访谈入口用现有 O2**（修 O2b-P0 后）。对话式 O2c 到位后无缝换。
5. **i18n / 合规 / 降级标注等既有纪律照旧**。分批交付，每批过 CI + 复审，**不搞大爆炸合并**。
6. **验收三问**：打开 3 秒知道做什么？每个按钮按下去是成品还是工具？数字有没有人话翻译？

# 第一章 · 为什么重建而不是修

## 1.1 走查实证（2026-07-30，生产 c8d08a5，手机端全新账号）

| 现象 | 判定 |
|---|---|
| 登录到首页可用 **约 10 秒，每次都是** | 非冷启动。首页渲染前串行等待业务状态机 / mission 计划 / agent 编排 / completion 校验 / journey 多路查询 |
| 点「开始 AI 访谈」→ Mission Workspace 显示 **验证 BLOCKED、Failed Checks 2**（`businessProfile.exists`、`aiInterview.completed`）、Required Assets 全 missing | **F-05 未修复**（原条目重开）。PR #187 修的是 P2023 造成的 500；F-05 真正的病灶是「访谈 CTA 路由到任务工作区，而访谈真身在 /brand-builder」，该路由错误从未被修。500 变成了一屏红色死循环，**用户结局相同** |
| 同一任务内 Required Assets 说 AI Interview = missing，Mission Steps 说「Open AI Interview 已完成」 | 状态源自相矛盾 |
| `businessProfile.exists` / `aiInterview.completed` / Passed Checks / Failed Checks / Depends / Outputs / COO Agent / Agent Support / Helper Team / BLOCKED / ACTIVE / LOCKED / missing | 内部状态机被整屏直接呈现（F-04/F-13/F-25 家族，规模更大） |

## 1.2 共同根因

**以上全部是「把后端状态机直接铺在屏幕上」的产物**，不是若干独立缺陷。

十秒加载与死循环是同一个病的两个症状：**为了显示一个按钮，先把整个业务状态机算一遍**。

新壳只需要一次查询（Brand DNA + 今天该做什么），十秒问题随重建自然消失，**不单独立项**。

## 1.3 旧用户面停止投入

**除合规红线外，旧用户面不再接受任何修复投入。** 第一批（#187/#188/#189/#190）照常上产，但其价值是修复底层 bug 与打通治理链，**不以「让走查通过」为验收标准**。

<a name="第二章"></a>
# 第二章 · 新壳三页规格

## 2.0 路由架构原则

> **阿姨的世界里没有导航，只有下一步。**

```
/                首页 —— 今天这一件事
/post            内容页（发）—— 保留为路由，供深链 / 通知跳转
/follow          跟进页（跟）—— 同上
/ads             插槽，W4 T5 实现前显示「即将开放」
```

**无底部 tab 导航。** `/post` 与 `/follow` 不通过导航栏抵达，只通过首页完成后浮出的入口、深链、或通知跳转。

---

## 2.1 首页 `/`

### 结构（自上而下，只有四层）

```
┌─────────────────────────────┐
│  今天先做这一件事            │  ← 一行小标
│                             │
│  【任务标题】                │  ← 一句人话，非英文、非内部名
│  一句为什么（可折叠）         │
│                             │
│  ┌───────────────────────┐  │
│  │      主按钮            │  │  ← 唯一的主行动
│  └───────────────────────┘  │
│  预计 X 分钟                 │
└─────────────────────────────┘

（完成后才浮出）
  ┌──────────────┐ ┌──────────────┐
  │ 还想发一条    │ │ 看看要跟进谁  │
  └──────────────┘ └──────────────┘

─────────────────────────────
第 X 天 · 已发 X 条 · 今天做 X     ← 底部一行，见第三章
```

### 硬性规则

- **一张卡、一件事、一个主按钮。** 完成之前，页面上不出现第二个行动
- 两个次级入口**只在今天这件事完成后浮出**，不是常驻
- **底部一句是唯一的进度呈现**。无卡片、无清单、无百分比、无 mission 机件
- 零内部字段名、零英文标签、零倒计时、零评分
- 空数据模块不渲染（既有纪律）

---

## 2.2 内容页 `/post`（发）

### 结构

```
今天这条（已经生成好，不用她按生成）
  ├─ 文案（可编辑）
  ├─ 配图指引  ← visual_guide 三字段：拍什么 / 怎么拍 / 避开什么
  ├─ 【复制文案】
  └─ （复制后原位出现）发好了点这里 ✓
```

### 关键交互：复制 → 打卡二连 ⭐

**「我发了」不做成孤立按钮。** 她点【复制文案】之后，**原位**出现「发好了点这里 ✓」。

一次点击同时完成三件事：

1. **计数** —— 「已发 X 条」的数据源
2. **多巴胺时刻** —— ✓ 动画 + 一句夸（教练语气，非机械提示）
3. **周活 / 连续天数数据源** —— 未来留存分析的唯一真实信号

> **设计要点**：系统看不到她在 FB 的实际发布行为。这个按钮是**唯一**的真实完成信号。
> 因此它必须出现在她动作的自然路径上（复制之后），而不是另起一个需要她想起来去按的按钮。

### 配图指引

来自 G1 输出的 `visual_guide` 字段（`what` / `how` / `avoid`），素材源为《配图拍摄指引 v1》，**不由模型自由发挥**。

轨道分套：招募号与零售号画面语言完全不同（见配图指引第二、三部分）。

### 其他

- 批量生成能力保留（后端一次生成 7/30 天），**默认视图一次只露一条**
- 「一次看全部」开关，用户自选，系统记住偏好
- 高级模式（批量重生成 / 整批调方向 / 批量导出 / 排期拖动）：开关打开才出现

---

## 2.3 跟进页 `/follow`（跟）

### 结构

```
今天要跟 N 个人

  陈小姐 — 昨天看完了，还没说话
    建议这样说：「……」  【复制】

  林太太 — 发出去 3 天没回
    建议这样说：「……」（三选项）  【复制】
```

### 硬性规则

- **不显示状态机。** 她看到的是「这个人现在怎么了」的人话，不是状态名
- 每条只给**一句该说的话** + 一个复制按钮
- 状态由事件自动推进，**不要她判断**。⚠️ **修订一**：批 3 只用**现有信号**驱动——留资料时间戳、她标记的对方反应。**webinar 播放进度事件留接口字段，W4/T3 落地后接入**；批 3 不得依赖它，否则会隐性阻塞在 T3 上
- 话术全部取自《事业包话术全集 v1》第三章，按状态取用
- WhatsApp 两态：**未接 API（默认）= 她自己回**；已接官方 API = AI 自动回。**两态共用同一话术库**
- 第一批只做未接 API 那一态，**API 抽象层留好**

---

## 2.4 「投」`/ads` — 插槽

W4 T5 实现前，显示「即将开放」占位。不做假页面、不做灰按钮。

## 2.5 ⭐ 我的账号（轨道的数据地基）

### 核心设计

**轨道 = 内容要发到哪个账号。**

不是让阿姨回答「我今天做零售还是招募」（决策问题），而是「你有哪几个号」（**事实问题**）。

### 数据结构

```
账号
  ├─ platform   FB / IG / 小红书 / TikTok
  ├─ track      recruitment / retail
  ├─ name       她填的号名（也是内容页切换器显示的文字）
  ├─ url        可选
  └─ enabled
```

### 为什么必须在批 1

- 目前 Funnel 表无 track 列，账号也无轨道归属——**「一个号 = 一轨」这个已定的设计在数据层根本不存在**，现状只有生成时传一个 mode 参数
- 它是「发」这一键第 0 步（开号引导）的落点
- 批 2 内容页要用它做轨道判定，不能等
- 与 `businessStartAt` 同属字段级新增，**一起迁移只需做一次恢复演练**

### 由它派生（结构要支持，本批不实现）

| 用途 | 依赖 |
|---|---|
| 「发」内容发往哪个号、用哪一轨 | 批 2 |
| 「投」boost 哪个号的帖子 | W4/T5 |
| 「跟」名单从哪个号的漏斗进来 | 批 3 |
| 数据回流按号分开统计 | 后续 |

### 新人默认状态

**只有一个招募号。** 系统在她开零售号之前，不显示任何零售相关的东西——**这是默认状态，不是例外分支**。

### 轨道在三页的呈现

| 页面 | 呈现 |
|---|---|
| 首页 | **不出现轨道概念**。今天这一件事就是一件事，不问她哪一轨。系统内部知道，她不需要知道 |
| 内容页 | 只有一个号 → 无任何选择；两个号 → 顶部切换器，**显示她的号名**，例：`[ Steven｜20年在家工作 ] [ 每天一杯，慢慢变好 ]` |
| 跟进页 | 名单从哪个号进来就带哪一轨，自动分开管。她看到名字和该说的话，**不看到轨道标签** |

> ⚠️ **切换器显示号名，不显示「零售 / 招募」内部词。** 她认得自己的专页名字，不认得「轨道」这个概念。这是术语层规矩的具体应用——实现时最容易被简化成两个写着「招募」「零售」的 tab。

### 跟进信号源的位置预留

「我的账号」与名单归属结构中，为跟进状态机的事件源预留位置：

- **已有信号（批 3 实现）**：留资料时间戳、她标记的对方反应
- **未来信号（W4/T3 落地后接入）**：webinar 播放进度事件

批 1 不实现任何跟进逻辑，只确保数据结构不排斥这两类事件源。

> 理由：批 3 若临时加字段，其形状很可能与 T3 实际产出的事件不匹配，届时仍需返工。**留位置的成本接近零，返工的成本不是。**

# 第三章 · 底部那一句

## 3.1 分阶段（一句话也要分阶段，这正是教练感）

### 体验期（Day 4 闸门通过前）

```
体验第 X 天 · 今天的奶昔喝了吗？
```

与事业包首周带法同拍：Day 1 产品介绍 + 冲泡教学 + before 照 → Day 2 使用确认 → Day 4 体验闸门。

### 事业期（Day 4 闸门通过后）

```
第 X 天 · 已发 X 条 · 今天做 X
```

## 3.2 「第 X 天」起算 ✅

**起算日 = Day 4 体验闸门通过日**，新增字段 `businessStartAt`。

不是注册日。理由：事业包定的「喝到有感觉了才会开始跟他规划下一步」——**体验有感 = 事业开始**。注册日起算会让还在体验期的人看到「第 8 天你才发 2 条」这种不公平的句子。

## 3.3 「已发 X 条」永不说谎 ⭐

**词汇自动切换，句子永远诚实：**

| 条件 | 显示 |
|---|---|
| 有「发好了 ✓」记录 | 已**发** X 条 |
| 只生成未确认 | 已**准备** X 条 |
| 都没有 | 该句不渲染（空数据不渲染，既有纪律） |

> **这条是硬规则不是文案偏好。** 系统看不到她在 FB 的实际发布，若无人点确认仍显示「已发」，这句话就是谎话。
> 与 G5「失败可见」同一条原则：**系统不得声称它不知道的事。**

## 3.4 边界

- **一行封顶**，不换行、不加卡片、不加百分比、不加图标条
- 完整视图（mission / 进度 / 验证 / agent）归 super admin
- 这一行就是修正案说的「AI 数字翻译」层：**数字永远带着「所以你今天做什么」**

# 第四章 · 「今天做什么」决策逻辑

## 4.1 定案：(a) 节奏表打底 + (c) 跟进插队

**全确定性逻辑，不过 LLM。** 这句话必须便宜、快、永不出错。

```
if (有名单等回复超过 24 小时) {
    今天 = 跟进       // (c) 插队
} else {
    今天 = 节奏表[当前天数]   // (a) 打底
}
```

## 4.2 节奏表内容源

**事业包首周带法 / 首月任务线**，不是新设计。

| 阶段 | 来源 |
|---|---|
| 体验期 Day 1-4 | 事业包一・五（收货前 → Day1 → Day2 → Day4 闸门） |
| 事业期第一周 | 开号引导（第 0 步）→ 发第一条 → …… |
| 事业期第二周起 | ⬜ **待补**：事业包 Day 4 之后的带法尚未口述 |

## 4.3 明确不用 (b) 现有 mission 引擎

**理由**：mission 引擎的输出形状（Business Goal / Mission / Agent / Completion Verification / Helper Team）**正是信息墙的来源**。让它退休到 admin。

> 护栏第 1 条「后端复用」指的是**服务与 API**，不强制复用这一层。

## 4.4 跟进插队的判定依据

「有名单等回复超过 24 小时」由跟进状态机（第二章 2.3）的事件时间戳决定，同样是确定性判断，不过 LLM。

# 第六章 · 旧页面处置

# 第八章 · 验收标准

## 8.1 阿姨测试三问（护栏第 6 条）

每一批交付都要过这三问：

1. **打开 3 秒知道做什么？**
2. **每个按钮按下去是成品还是工具？**（成品 = 可以直接用的东西；工具 = 还要她自己操作的界面）
3. **数字有没有人话翻译？**（数字后面必须跟着「所以你今天做什么」）

## 8.2 端到端计时走查（全部交付后）

```
全新账号（SA1 重置）→ 手机 → 计时开始
1. 注册 / 登录
2. 首页第一个按钮是什么？点下去有没有卡住 / 报错 / 看不懂
3. 走完访谈
4. 不补任何资料，直接生成第一篇内容
5. 生成 → 编辑 → 复制 → 点「发好了」→ 真的发到 Facebook
计时结束
```

**只记三件事**：总用时几分钟、中途在哪几步停下来想「这是什么意思」、有没有任何一步要绕行才能过去。

## 8.3 硬性回归

- 零内部字段名入 UI
- 零英文标签（未走 i18n 的）
- 零「AI COO」（全站改「AI 教练」）
- ⚠️ **修订三 · 性能硬指标**：**首页可交互 ≤ 3 秒**（手机 4G、新账号）。
  需**实测数字**，不接受「明显变快」这类描述——「明显低于」无法回归测试。
  旧壳基线为 10 秒且每次如此（非冷启动）。
