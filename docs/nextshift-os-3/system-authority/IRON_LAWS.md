# Iron Laws

Version: 1.0

Status: Current

Last Updated: 2026-07-08

---

## Non-Negotiable Rules

1. Higher authority overrides lower authority.

   Governance, foundation, constitution, reference architecture, contracts, standards, and approved status documents override implementation details and generated artifacts.

2. Understand the system before changing the system.

   Read the system authority, system context, blueprint, MVP alignment, current statuses, and engineering playbook before proposing architecture, workflow, or capability changes.

3. The Business Twin is the center.

   NextShift is an AI Guided Business Operating System. It is not merely a CRM, funnel builder, content tool, chatbot, or task app.

4. The core intelligence loop must remain intact.

   Observe -> Understand -> Reason -> Recommend -> Discuss -> Decide -> Execute -> Measure -> Reflect -> Learn -> Improve.

5. Do not duplicate authority.

   Extend the current authority or propose an RFC. Do not create parallel v1.0 systems, duplicate playbooks, duplicate orchestration models, or duplicate standards.

6. Engineering Playbook v1.2 is the current engineering workflow authority on this branch.

   Do not propose `Engineering Orchestrator v1.0`. Do not invent `Engineering Playbook v1.3` unless an approved source document, RFC, release record, and audit record exist.

7. Historical evidence must remain historically accurate.

   Old audit, release, verification, implementation, capability, and generated package files may mention retired baselines. Preserve them unless a file is reclassified as current authority.

8. Generated artifacts are evidence, not authority.

   Packages under generated artifact folders may contain snapshots. They must not override current source files under `docs/nextshift-os-3/`.

9. Status files are control surfaces.

   Do not change Blueprint, Runtime, Capability, Workflow, Repository, or Project status files casually. Status changes need evidence and validation.

10. Every material change needs traceability.

    A serious change must have planning, implementation evidence, verification, audit, and release or handoff records as appropriate.

11. GitHub alignment matters.

    If local and remote branches disagree, inspect branch evidence before advising. Do not assume the local folder, default branch, or latest-looking file is authoritative.

12. No secret leakage.

    Never place live credentials, `.env` contents, Supabase service-role keys, database passwords, or private API keys in docs, artifacts, prompts, commits, logs, or handoff packages.
