## 1. 核心判决(代码证实)

用户的核心日常闭环应为:**生成 → 编辑 → 保存 → 导出/发布**。现状:

| 环节 | 现状 | 证据 |
|---|---|---|
| 生成 | ✅ 有(AI 多平台文案) | ContentCommandCenter 挂在 /content-engine |
| **编辑** | ❌ **完全缺失** | 活组件 966 行,textarea/isEditing/contentEditable 计数 = 0 |
| 保存 | ⚠️ 服务端静默入库,用户不可见不可控 | contentEngineService `prisma.content.create`;无内容库页面,存了等于没存 |
| **导出/复制** | ❌ **完全缺失** | 活组件 clipboard/writeText 计数 = 0 |

**闭环四环断三环。** 产品当前形态是"AI 演示器",不是工作工具。

### 1.1 最重要的考古发现

编辑/复制/保存能力**曾经存在**:死组件 `ContentEngineDashboard`(无任何路由引用)里有生成结果展示 + 复制 + 保存动作。某次迭代以 `ContentCommandCenter` 替换入口时,这些基础能力被留在了死代码里没有迁移。**这不是"没做过",是"做过又弄丢了"——AI 高速迭代不做能力清点的典型代价。**

## 2. 全面能力矩阵(按模块,组件级 grep 计数)

| 用户面 | 可复制 | 可编辑 | 可保存 | 判定 |
|---|---|---|---|---|
| content-engine(活口) | 0 | 0 | 0 | ❌ 核心面,最重灾 |
| video | 3 | 1 | 0 | ⚠️ 半闭环,产出无法留存 |
| brand-builder | 3 | 4 | 7 | ✅ 相对完整(参照系) |
| funnel | 2 | 7 | 1 | ⚠️ 可编辑,导出/发布弱 |
| lead-magnet | 0 | 0 | 0 | ❌ 纯展示壳 |
| webinar-center | 0 | 0 | 0 | ❌ 纯展示壳 |

**brand-builder 是全站唯一接近"工具"标准的面**——它的编辑/保存交互模式应成为其他面的统一范式,不必新发明。

## 3. "页面乱"的结构性成因

1. **死代码堆积**:content-engine 三个 dashboard 组件并存,两个无路由引用(ContentDashboard / ContentEngineDashboard)——维护者(包括 AI 执行者)每次都面对三倍的理解负担,改错对象的概率巨大(本审计自己第一轮就查错了组件)
2. **45 个 auth 路由,无信息架构总图**:路由由各版本累积生成,从未做过"用户视角的页面地图"盘点;哪些可达、哪些孤儿、哪些重复,没有单一事实源
3. **模式切换(Retail/Recruitment)双导航**:同一功能在不同模式下入口不一致,加剧迷路感
4. **卡片/面板视觉方言混杂**(前次 UI 审计的 3,519 逃逸 + 24 套 Card 的延续)——每页看起来像不同产品
