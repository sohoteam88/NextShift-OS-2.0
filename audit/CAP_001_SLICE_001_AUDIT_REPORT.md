## Medium Issues

### M-001 — Application imports concrete `BusinessBrain` class rather than `BusinessBrainContract`

**Package:** application  
**Location:** `application/src/business-profile/index.ts`

```ts
// Current
import type { BusinessBrain } from "@nextshift/business-brain";

export class CreateBusinessProfileUseCase {
  constructor(private readonly businessBrain: BusinessBrain) {}
  ...
}
```

The use cases accept the concrete `BusinessBrain` class as a constructor parameter rather than `BusinessBrainContract`. The contract WAS correctly updated to include `createBusinessProfile` and `getBusinessProfile`, so an interface-based approach is available. Importing the concrete class:

1. Couples use cases to the `BusinessBrain` implementation — future alternative implementations must be the same concrete class or subclass
2. Reduces testability — test doubles must be subclasses or the full class, not lightweight contract implementors
3. Exposes all public class methods to the use case, not just contracted methods

**Impact:** Functions correctly today. Risk when a database-backed `BusinessBrain` implementation is introduced — the constructor type would need updating across all use cases.

**Action for Codex:** Change use case constructor parameters to `BusinessBrainContract` and adjust return types (`Result<BusinessProfileRecord>` from the contract) or create a dedicated `BusinessProfileService` interface that covers only the three methods used by this slice.

## Low Issues

### L-001 — Parallel type hierarchy creates drift risk

**Packages:** domain, contracts

The domain and contracts packages define structurally identical types independently (required by the "contracts cannot import domain" rule):

| Domain type | Contracts type | Structurally identical? |
|---|---|---|
| `BusinessIdentity` | `BusinessIdentityPayload` | ✅ yes |
| `BusinessProfileMetadata` | `BusinessProfileMetadataPayload` | ✅ yes |
| `BusinessProfile` | `BusinessProfileRecord` | ✅ yes |
| `BusinessStage` | `BusinessStage` | ✅ yes — defined twice |

These are intentional — contracts cannot import domain, so payload types must be defined independently. TypeScript's structural typing ensures compatibility. However, when a new field is added to `domain.BusinessIdentity`, it must also be manually added to `contracts.BusinessIdentityPayload`. There is no compile-time guard enforcing this.

**Impact:** Low at this slice scope. Risk grows as more identity fields are added in future slices.  
**Action for Codex:** When adding fields to domain identity types, always mirror them in the corresponding contracts payload types in the same commit.

### L-002 — Dead `BusinessProfile` type remains in `domain/src/business/index.ts`

**Package:** domain  
**Location:** `domain/src/business/index.ts`

The old bootstrap `BusinessProfile` interface (shape: `{ businessId, tenant, name: string, createdAt }`) is still present in `domain/src/business/index.ts` but is no longer exported (the `domain/src/index.ts` now does `export type { BrandDNA } from "./business"` — only `BrandDNA` is re-exported).

The unexported `BusinessProfile` in `business/index.ts` is dead code. It has a different shape from the canonical `BusinessProfile` in `business-profile/index.ts` (which uses `identity: BusinessIdentity` rather than `name: string`). This could confuse future developers reading the file.

**Impact:** No runtime effect. No type conflict (not exported).  
**Action for Codex:** Remove the dead `BusinessProfile` interface from `domain/src/business/index.ts`.

### L-003 — Event ID generated by string concatenation

**Package:** event-bus  
**Location:** `event-bus/src/business-profile/index.ts`

```ts
eventId:
  input.eventId ??
  (`${input.businessId}:business-profile-created:${input.occurredAt}` as EventId),
```

The fallback event ID is generated by concatenating `businessId` and `occurredAt`. Since `occurredAt` is an ISO string (millisecond precision), two `BusinessProfileCreated` events for the same `businessId` within the same millisecond would produce the same `eventId`. This is an edge case but `EventId` semantics imply uniqueness.

**Impact:** Near-zero risk at bootstrap scale. Must be addressed before production.  
**Action for Codex:** Replace the fallback with a UUID generator (e.g., `crypto.randomUUID()`) before production deployment.

## Architecture Risk Review

| Risk | Assessment |
|---|---|
| **New dependency direction** (`business-brain → domain`) | Clean. Declared in package.json and tsconfig. No circular risk. ✅ |
| **Event payload shape** | Structural. `BusinessProfileCreatedPayload` is a data type only. Parallel type hierarchy (contracts ↔ domain) requires manual sync (L-001). |
| **In-memory storage boundary** | `BusinessProfileStore` interface is correctly placed. `InMemoryBusinessProfileStore` is clearly a bootstrap implementation. Future DB store can be injected. Low risk. |
| **Business Twin snapshot mapping** | `getBusinessContext()` maps domain fields to `BusinessIdentityContext`. Mapping is explicit and type-safe. Future slices (Brand, Offer, Customer, Goals) will need to extend this mapping. Low risk. |
| **Future API integration** | Use cases are clean. `CreateBusinessProfileCommand` and `GetBusinessProfileQuery` carry `ApplicationContext` which includes tenant and actor. API layer can build these easily. No risk. |
| **Future database persistence** | `BusinessProfileStore` interface is the injection point. Replacing `InMemoryBusinessProfileStore` with a database implementation requires no changes to `BusinessBrain` logic. Well-structured. |
