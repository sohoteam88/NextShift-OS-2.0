## CP1 — F2 Twin de-duplication (resolves prior C-2)

**Requirement (blueprint F2 / prior audit C-2):** de-duplicate at the **repository** layer so the system prompt carries each fact once — `mission`/`positioning`/`brand.positioning` collapse when equal, `businessName`/`brandName` collapse when equal; `buildTwinSummary` stays dedup-unaware; empty-after-dedup contexts are omitted; existing Twin tests lose zero assertions.

**Every property is real and independently tested.** `deduplicateTwinContexts` (`interview-brand-business-twin-repository.ts:101-145`):

- **Name family** — if `identity.businessName` equals `brand.brandName` under normalization, `brand.brandName` is dropped (`:108-115`). The higher-priority `identity.businessName` is never dropped. ✓
- **Positioning family, priority-ordered** — `retainedPositioningValues` is seeded with `identity.positioning` (always retained, highest priority, `:119-121`); `identity.mission` is dropped iff its normalized value already matches a retained one, else it is itself retained (`:123-131`); `brand.positioning` is dropped iff it matches any retained value (`:133-139`). This is exactly `identity.positioning` > `identity.mission` > `brand.positioning`, "omit when equal to a higher-priority field." I hand-traced the four cases (all-three-equal; positioning-absent + mission==brand; positioning≠mission + brand==positioning; positioning≠mission + brand==mission) and each collapses correctly with no over- or under-drop. ✓
- **Comparison normalization matches the prompt formatter** — `normalizeTwinValue` (`:151-153`) does `trim` + `\s+→' '`, the same transform `formatTwinField` (`discussion-service.ts:415`) applies before emitting. A dropped field therefore could only have produced an identical prompt line — no false drops. **Original values are retained; only the comparison is normalized** (`:113,126,136` destructure the original object). ✓
- **`buildTwinSummary` is dedup-unaware** — the discussion-service diff adds *only* `maxLength` arguments; it contains no dedup logic (`discussion-service.ts:394-404`). ✓
- **Empty-after-dedup context omitted** — `hasContextFields` re-applies the `Object.keys().length > 0` guard after dropping, so a `brand` reduced to `{}` becomes `undefined` and the `...(brand ? …)` spread omits it (`:141-144`, `:45-46`). ✓

**Real-data path confirmed, not just the fixtures.** `BrandProfileAdapter.ts:120` (`pickString(profile, ['brandPositioning', …])`) and `BrandContextProvider.ts:35` (`positioning: bp.brandPositioning`) mean the three positioning fields and the two name fields genuinely coincide for a BrandProfile user — so the dedup **fires on the production path**, not merely on constructed inputs. This is the exact scenario the prior F-5/C-2 traced as live prompt noise; it is now collapsed to one line per fact.

**Tests are substantive and honest** (`interview-brand-business-twin-repository.test.ts`):
- `omits whitespace-normalized duplicate name and positioning facts` — feeds `missionStatement` with a double-space + newline variant of the positioning string and asserts `mission` is dropped while `positioning` (original value) survives, plus `brand.brandName`/`brand.positioning` dropped. Proves normalization-based comparison, not literal equality. ✓
- `keeps every non-colliding source fact` — blanks `brandName`/`positioning` on the brand context and asserts all four identity fields and both remaining brand fields survive (`toEqual`, exact-shape). Guards against over-dedup. ✓
- `omits a Brand DNA context when de-duplication removes its final fields` — asserts the whole `brand` key disappears when dedup empties it. Covers the `hasContextFields` guard. ✓
- **Existing tests strengthened, not deleted** — the two pre-existing assertions that asserted the *duplicated* shape (`brand.brandName === 'North Star Wellness'`, positioning present) were converted to omission assertions plus a `businessName` retention assertion. These *had* to change because they asserted the prior bug; no coverage was removed. ✓

**Result: CP1 PASS — prior C-2 resolved.**
